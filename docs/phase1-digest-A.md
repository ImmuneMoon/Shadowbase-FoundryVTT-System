# Phase-1 digest A — data model, engine, rolls, effects, catalogs

Key facts recovered from the 2026-09-07 subsystem readers (the full reports were lost with the temp scratchpad; these are their returned key facts, verbatim where possible). Every fact cites the website (`../ShadowBase Website/src`) and was verified by its reader against source at the time. Where a fact matters for a build decision, re-verify against the current source before relying on a line number.

## schema-core (CharacterFormValues, trait/skill/power rows, modifier bag, droidBuild)

1. The engine entry point is `getCalculatedStats(values: CharacterFormValues): CalculatedStatsResult` in `src/hooks/use-character-calculations.ts` (line ~143); it consumes the FLAT form shape, not the export JSON, and expects it spread over `blankSheetData` first (`{ ...blankSheetData, ...incoming }`, `use-character-form.ts` ~line 213).
2. Zod defaults never fill absent keys at runtime because the website never runs `characterSheetSchema.parse()` on load (only on save/export/PDF); `blankSheetData` (`src/lib/templates/custom/blank-sheet-template.ts`) is the real default source and seeds a Credit Chip equipment row and the 12-row STANDARD_HUMANOID_ANATOMY with fresh uuids.
3. Firestore stores the flat form values plus `lastSaved`, with the sanitized character name as the document id; the nested export JSON (`convertSheetToJson`/`convertJsonToSheet`, `docs/CHARACTER_JSON_FORMAT.md`) is the interchange format third-party tools (Waypoint) emit.
4. `strength/dexterity/iq/health` and `hitPoints/will/perception/frightCheck/vision/hearing/tasteAndSmell/touch/endurancePoints/forcePoints/basicSpeed/basicMove` are null-means-derive; a literal number is a priced purchase; droids must keep all four primaries null or the stored value silently overrides the hardware base (`getPrimaryAttributes`: raw = stored ?? restingValue).
5. `currentHitPoints/currentEndurancePoints/currentForcePoints` are null-means-FULL sentinels filled on load by `fillUnrecordedPools` from `currentValues.hitPoints/endurancePoints/maxForcePoints`, then `applyForcePointCeiling` clamps FP downward only.
6. `derivedBase` (printed figure from raw attributes; what attribute points price against) and `currentValues` ((manual ?? base) + modifier; what rolls) are produced together by `getCoreCharacteristics(formValues, primaryAttributes, globalModifiers, fpCandidates)`; modifiers are applied inside it and nowhere else; the point engine re-runs it with zeroed modifiers so gear never prices.
7. Pricing: `POINT_COSTS_PRIMARY` ST 10 / DX 20 / IQ 20 / HT 10 per level from `<attr>Baseline` (Size Discount on ST); `POINT_COSTS_SECONDARY` HP 2, EP 3, Will 5, Per 5, FP 3, Basic Speed 20 per whole point, Basic Move 5, Fright 2, each sense 2, priced as (manual − derivedBase) − `<row>Baseline`; droids pay nothing for attributes.
8. Trait rows (advantage/disadvantage/quirk) are the only rows PROJECTED onto their zod schemas on export and import (`projectSchemaFields` drops undeclared keys, aliases notes→description); every other row kind is copied whole.
9. Advantage charge = `chargeForAdvantageRow(row, sizeModifier)` = max(0, points − baselinePoints) when baselinePoints > 0 (a granted row cannot be sold back), size-discounted for Striking/Lifting/Arm ST; disadvantages and quirks charge points − baselinePoints unclamped; only the first `MAX_QUIRKS` = 5 quirks bill.
10. A trait row's modifier bag is resolved by `traitModifiersFor(row)` (`src/lib/trait-level-modifiers.ts`): library level bag, then library flat bag, then the stored row bag (only for names the library does not know); rows whose name another present row `includes` grant nothing (`traitRowsThatGrant`).
11. Skill rows store `level` as a STRING (engine parseInts), `relativeLevel` like "DX/Easy" or "IQ/Hard-2" carries the pricing basis, `points` is not the price; cost = `calculateCostForSkill(skill, skillPricingAttributes)` via `SKILL_POINT_COST_TABLE`, charged through `chargeForGrantedRow(cost, baselinePoints)`, against base-plus-trait-modifier attributes with no gear.
12. forcePower and combatTechnique sheet rows are the catalog row spread whole (one catalog row per name+level; 147 powers, 56 technique rows) and charge cpCost − baselinePoints; `combatTechnique.category` is a strict enum Melee|Unarmed|Ranged|Universal and `selectedWeaponId` is a host reference to a weapon row id.
13. lightsaberForms rows store only name, level, baselinePoints (plus custom/effect/tierEffects/confirmed for homebrew); the exporter enriches from the catalog and the importer reads only name/level/baselinePoints; cost = `getFormDetails(name, level).cpCost` − baselinePoints on a 10/20/35/55 ladder.
14. The modifier bag has exactly 25 channels declared once in `src/lib/modifier-channels.ts`: 23 summed numerics (strength, dexterity, iq, health, will, perception, move, dodge, dr, carryCapacity, endurancePoints, forcePoints, toHit, basicSpeed, hitPoints, frightCheck, parry, block, stunRecovery, strikingSt, liftingSt, kickDamage, jumpDistance), `frightImmune` (boolean, OR) and `moveMultiplier` (identity 1, Math.min); always spread `NO_MODIFIERS` and test with `hasAnyModifier`.
15. `statusEffectSchema` rows carry a FULL bag plus id (string, not uuid), name, type buff|debuff, source, description, isManual, isGear, duration, expiresAfterTurn (turn sweep removes when turnCounter passes it), phases[] and phaseIndex; a phase's `modifiers` is a partial numeric record and its `endurancePoints` value is an EVENT deducted from the current pool by `applyCrashPhase`, not a max modifier.
16. Only manual effects, stimulants, Shock, activated armor buffs/recharges and crashes are STORED in `statusEffects`; every gear, trait, implant, saber-part, set-bonus, form, encumbrance, stun, alignment and conditional row is derived each calculation into `activeStatusEffects` and summed into `globalModifiers`.
17. `globalModifiers.dr` from rows with isManual or source === 'Advantage' becomes innate DR on every hit location; gear DR is applied per location instead, so gear `dr` must not be fed into the global sum.
18. `hitLocations` rows need a stable v4 uuid id (armor drEntries, implants' installedHardwareIds and recorded damage key on it); droids derive their anatomy from droidBuild via `droidAnatomy` (T20 table, deterministic ids from `droidLocationId(slot)`) and `reconcileDroidAnatomy` carries status/currentDegradation/isAmputated/installedHardwareIds across by name|side, never innateDR.
19. droidBuild's slot arrays (head.sensorIds, chassisMods.internalIds/externalIds/utilityIds/auxiliaryIds/motiveMountIds) are SPARSE by contract — index is the slot identity, internalIds[99] is the Backup Power Array, holes are null-filled by `sanitizeDataForFirestore` and must never be compacted.
20. `languageEntries` is the one billing home for languages (native/granted 0, broken 1, accented 2, fluent 3, comprehension-only 1/1/2 via `languageEntryCost`); the `languages` string is a bracket-free display projection; `culturalFamiliarities` and `literacy` are text-billed by `;`-separated `[n]` brackets minus their `*Baseline`.
21. Species packages (`SPECIES_PACKAGES` in `src/lib/species-swap.ts`) apply only marked trait rows (fromSpecies), sizeModifier, height/weight and the language/familiarity/literacy lines; racial attribute modifiers are trait rows named `<ST|DX|IQ|HT|Will|Perception> +N (Racial)` with points 0, never baked into values or baselines.
22. Load pipeline order: migrateSanitizerNulls, blank-sheet spread, migrateSkillNames, migrateMeleePowerCells, migrateCyberneticNames, migrateSpeciesNames, migrateTraitNames, migrateRacialTraitNames, migrateEnhancedDefenses, migrateLanguages, migrateLanguageEntries(data, skillPricingAttributes), migrateFacing, migrateFoldedSkillBonuses, migrateLightsaberDurability, ensureCompleteArmorItem, ensureCompleteStarshipItem, enforceBaseLayer, fillUnrecordedPools, applyForcePointCeiling (now `applyLoadMigrations` in `src/lib/load-sheet.ts`).
23. Fields stored but NOT in the export JSON (a round trip loses them): activeLightsaberForm, activeFormWeaponId, parriesThisTurn, pointsOther (the last is a real input read by `calculateSpecialAbilityPoints`).
24. Dead root fields (no writer or reader in src/): trackPurchases, incomingArc (consumed by migrateFacing on import only), the root currentValues object, pointsAttributes/pointsAdvantages/pointsDisadvantages/pointsSkills, spentPoints, remainingPoints, basicLift, damageThrust, damageSwing, parry, block, drHead, drTorso, lastSaved, root flawedBuild.
25. Row ids on trait/skill/power/technique/form rows are optional but validated as v4 uuids when present; storageBoxes.id, hitLocations.id, droidBuild.arms[].id/legs[].id are required uuids — Foundry 16-char ids cannot satisfy this, so rows keep website uuids (minted with `crypto.randomUUID` when absent).
26. The old Foundry `template.json` defaults (attributes.value 10, characteristics 0 with points/max keys) contradict null-means-derive.
27. The website's format doc says `shipPosition` is object|null but the schema and the crew-position select store a string; the code wins.
28. `useLiftingST/useStrikingST/useArmST` are `z.boolean().optional().default(true)` (order matters), seeded true by the blank sheet, exported under `investment.*`; `false` is a player choice read with `??`.
29. `forceAlignment` is a stored integer in [−100, 100] with tiers at |A| ≥ 25 (Aligned) and ≥ 75 (Deeply Aligned); 0 is real; the importer derives it from lightSidePoints − darkSidePoints only when absent.

## schema-inventory (the 16 inventory arrays)

1. `ITEM_KINDS` (`src/lib/item-transfer.ts`) defines 15 kinds mapped to 14 form arrays: lightsaber, customBlaster, customMeleeWeapon, customExplosive, armorItem, armorModification, weaponModification, ammunition, neuralImplant, cyberneticLimb, cyberneticUpgrade, customStarship, vehicle, blueprint (equipment rows with non-empty blueprintOf), generalEquipment.
2. customStarships and vehicles are two arrays in memory but one array in the JSON (`inventory.starships`); the importer splits them back by `'baseChassis' in row`; within vehicles Terrestrial/Atmospheric split by `vehicle.category`, else VEHICLE_DATA category, else type Groundcar/Speeder.
3. `lightsaberModificationSchema` is literally the same Zod object as `weaponModificationSchema`; the two arrays differ only by which resolvers read them (Foundry merges them into `weaponPart` with a family discriminator and re-splits on export).
4. Parts are never copied onto their host: a fitted part stays in its own array flagged equipped + isInstalled + installedIn{Saber,Melee,Blaster,Armor}Id, and carried weight/cost skip it because it is inside the host's finalWeight/finalCost (`calculateEquipment.ts`).
5. Slot objects: `modularPieceSchema` {partId, materialId, inventoryId} (blaster slots), `meleeComponentEntrySchema` (+quantity, as lists gripParts/headParts/guardParts/utilityParts), `lightsaberSlotSchema` (+wrapId, nine hilt slots), `armorComponentSlotSchema` {partId, inventoryId} (shellPart/backingPart/framePart/visorPart/trimPart); all resolve "owned row by inventoryId wins, else the slot's own catalog partId/materialId is a chosen-not-owned design".
6. Bought-finished goods use a bare uuid field plus a `*PartId` catalog companion: 7 saber internals (powerCell, lens, emitterMatrix, primaryCrystal, powerCrystal, primaryCrystalTwo, powerCrystalTwo) and 13 blaster mod slots (`RANGED_MOD_SLOT_FIELDS` in fitted-goods.ts); armour's four mod slots (integratedModId/overlayModId/underlayModId/utilityModId) and melee's three treatments have no companion; `PART_ID_FIELDS` in installed-attachments.ts is the authoritative list.
7. Weapon durability uses null as the "not measured" sentinel (0 = Broken, −1 = Destroyed); maxDurability derives from components; `trackedDurability` (durability-tracking.ts) makes a design (isConstructed false) track its maximum and a built weapon hold a reading; `conditionFromDurability` and `MALF_BANDS` (17/16/15/14 at ≥76/51/26/1 %) live in malfunction.ts.
8. Armour condition is read off DR, not durability: `calculateModifiedArmor` derives Broken when every drEntries[].dr is 0 against a measured listed DR and Damaged when any entry is below `listedArmorDrAt`; `drEntries[].dr` IS the tracked current DR per hit location; durability on armour is Clothing-only and forced to 0 otherwise by `ensureCompleteArmorItem`.
9. Each card hook writes derived fields back onto the stored row on mount: blaster (`calculateBlasterStats`, pure) writes finalDamage/finalDamageType/finalAccuracy/finalHalfDamageRange/finalRateOfFire/finalWeight/finalCost/finalBulk/finalRecoil/finalST/notesAndEffects/maxDurability/condition/energyRes/malfunction/totalUpgradesCost plus durability and reclassified baseType/baseSkill; melee writes damageModes/finalWeight/finalCost/finalParryMod/finalStRequirement/isUnbalanced/canParryWhileAttacking/baseReach/finalDamage/finalDamageType/energyRes/notesAndEffects/maxDurability/durability/condition; lightsaber writes 15 coreKeys plus durability/durabilityTwo; armour writes finalDRValue/finalWeight/finalCost/finalMovePenalty/finalDXPenalty/notesAndEffects/condition and mirrors the power cell's charges.
10. The armour final* caveat: finalWeight/finalCost/finalDRValue/notesAndEffects are stored on the row, carried through `ensureCompleteArmorItem` untouched and recomputed only when that card mounts; Carried Weight ignores them and calls `calculateModifiedArmor` per row on every read, while the exporter stamps recomputed figures (at SM 0 with no hitLocations).
11. `ensureCompleteArmorItem` rebuilds the row from an explicit field list and drops anything unnamed (`armorItemSchema.flawedBuild` is NOT in that list — lost on every load).
12. `ensureCompleteBlaster/ensureCompleteMeleeWeapon` only default condition/malfunction/quantity/equipped (melee adds energyRes), but `ensureCompleteLightsaber` defaults durability/maxDurability/durabilityTwo/maxDurabilityTwo to 10, contradicting the null sentinel; `lightsaber-durability-migration.ts` undoes that.
13. Loading a pack moves it: `BlasterAmmunition.tsx` decrements or splices the source ammunition row and stores a quantity-1 copy in `loadedAmmunitionData` (currentCharges/maxCharges mirrored onto the blaster); `loadedAmmunitionId` may point at a row that no longer exists; unloading recreates/stacks the row; an equipment-sourced power cell stays in equipment flagged isInstalled + installedInBlasterId with `_isEquipSource: true` on the copy.
14. A shipped/library weapon is never one row: `buildTemplateBlaster/buildTemplateMeleeWeapon/buildTemplateLightsaber` (`templates/*-common.ts`) return the weapon plus 3–6 part rows (isInstalled, equipped, installedIn*Id, partId, materialId, shelf cost) and a loaded pack; a weapon row arriving without its parts is treated as an unbuilt shell (isConstructed cleared, partsMissing) by `parseImport`.
15. Implants and limbs are linked to the body in REVERSE: `hitLocations[].installedHardwareIds` names the implant/limb ids; the rows carry only `installed: true`; an implant grants its bag only when linked to a non-amputated location, not boxed, with no pathway conflict or slot overload; cyberneticUpgrade rows are flagged equipped and a COPY sits in `limb.upgrades[]`.
16. `installedInDroidId` is legacy (readers keep the sentinel 'PLAYER_DROID'); `installedInVehicleId` is on the import placement-strip list but declared by no schema.
17. Money is inventory: Credit Chips are one equipment row each with `storedValue`, Aurodium bars stack with `denominationValue`, and `sumCurrency` (currency-transaction.ts) totals category === 'Currencies' rows that are not boxed; `totalCredits` is an aggregate synced from them.
18. Ammunition rows are recursive (`contents: Ammunition[]` for magazines, `containerType` caliber), cost/weight are FULL values with baseCost/baseWeight the non-depleting casing, and depletedCost/depletedWeight derive the present value; `gasGrade` on Power Packs modifies the finished blaster line via `gasGradeEffect`.
19. Starship rows carry nine damage-tracking systems (engines, weapons, cockpit, sensors, power, shields, hyperdrive, lifeSupport, cargo) each {id, name, dr, hp, maxHp, status Nominal|Damaged|Disabled, notes} seeded by `initialSystems(hp, dr)` and refreshed by `mergeSystems` which never overwrites hp; armaments are {name, damage, skill}.
20. `gearSets` stores only custom outfits as {id, name, memberIds[] into armor}; the 19 handbook sets are recognised from inventory by name/setId and never stored; `storageBoxes` is a top-level {id, name, description} list and any row with `storageLocationId === box.id` is inside it.
21. Hands: readied weapons are rows with equipped && !storageLocationId sorted by equippedAt; `heldLocationIds` pins them to hit-location ids; `isWornWeapon` costs no hand; `isWeaponTwoHanded` reads saber classType/coupler, the blaster grip's Ch11 dagger mark, or the melee branch.
22. Proposed Foundry Item types (adopted): equipment, armor, blaster, meleeWeapon, lightsaber, explosive, ammunition, weaponPart (both modification arrays), armorPart, implant, cyberneticLimb, cyberneticUpgrade, starship, vehicle; gearSets/storageBoxes/hitLocations stay actor-level; splits needed for starships/vehicles, per-limb plates (`profileToArmorItem`), credit chips, template weapons with part rows.
23. The single-item envelope is `{__format:'shadowbase.item', __kind, __version: 2, __exportedAt, __note?, item, parts?: Record<formArray, rows[]>}`; `PARTS_SOURCES`: lightsaber→lightsaberModifications, melee→weaponModifications, blaster→weaponModifications+ammunition, armor→armorModifications; on import parts get fresh ids and are REBOUND to the new host id while placement on the item itself is stripped.
24. Open: `neuralImplantSchema` declares no `condition` field yet the engine reads `implant.condition`; `armorItemSchema.flawedBuild` is dropped on load; melee `currentCharges/maxCharges` fill 100/100 on first measure regardless of the printed column; `armorItem.type` is a free string but ARMOR_DATA uses exactly Clothing/Utility/Light/Medium/Heavy/Energy Shield/Accessory.

## engine-load-path

1. `getCalculatedStats(values)` is the sole engine entry; `calculateStatsPure` is an import alias. It is pure over plain objects; its result contains a Map (`skillBonuses`) and must never be persisted.
2. Eight load steps announce to the player (species rename, trait rename, languages updated, languages structured, folded skill bonus, saber durability restored, armor layering corrected, Force Points capped); the rest are silent. (Now returned as `notices` by `applyLoadMigrations`.)
3. `migrateLanguageEntries` calls `getCalculatedStats` on a half-migrated sheet (armor not yet rebuilt), so the engine must tolerate un-ensured armor rows.
4. `fillUnrecordedPools` is called with currentForcePoints = `currentValues.maxForcePoints`; `applyForcePointCeiling` only clamps downward and leaves negative (Force Exhaustion) totals alone.
5. The engine reads stored per-item derived fields: `saber.finalWeight` and `saber.totalCost`, `blaster.finalCost`, melee `finalCost`, blaster `finalST`, armor `finalMovePenalty/finalDXPenalty`; per-item derivations must run before the engine pass (the Foundry actor does a two-pass).
6. Pure per-item derivations: blasters `calculateBlasterStats(blaster, weaponModifications)`, armor `calculateModifiedArmor(item, armorModifications, characterSM, hitLocations)`, starships `deriveStarship/formatStarshipReadouts/initialSystems/mergeSystems`; melee and lightsaber are now `calculateMeleeWeaponStats` / `calculateLightsaberStats` (extracted 2026-09-10).
7. The melee derivation needs `primaryAttributes.effectiveStrength`, `damageStLevels` (one-handed) and `twoHandedStLevels`, chosen by `isWeaponTwoHanded(weapon, weaponModifications)` and gated by `values.useStrikingST`.
8. Hazards handled in the bundle: `character-sheet-helpers.ts` imports `FieldValue` from firebase (stub is a real class); template files call `crypto.randomUUID()` at module evaluation (polyfill before import); the per-item hook modules import react-hook-form (stubbed); `sanitizer-null-migration.ts` computes its key set from `characterSheetSchema` at load (zod stays real).
9. No localStorage/document access exists on the engine path; the UI modules that do (sheet-navigation, use-dice-roller, use-toast, use-sheet-preferences) are excluded.
10. Blank-sheet defaults: secondary characteristics null (derive); current pools null (full); pointTotal 150; powerPoints 100; useLiftingST/useStrikingST/useArmST true; totalCredits 7000 with a Credit Chip row.
11. After load the website keeps rewriting the sheet via effects Foundry must adopt or drop: relative sync of stored secondaries when derivedBase moves (reads derivedBase only), cpBaseline auto-adjust and baselinePoints seeding in non-starting-points mode, currency sync, tracked credit deduction, anatomy refit; `LOAD_REWRITTEN_FIELDS` (form-dirty.ts) = lightSidePoints, darkSidePoints, totalCredits, frightCheck, basicSpeed, basicMove, characterPortrait, cpBaseline.
12. The engine synthesizes status effects with stable ids (implant-*, limb-*, upgrade-*, ls-part-*, ls-crystal-attunement, force-alignment-tier, auto-<name>, hardware-failure, stunned, mathematically-inclined, critical-power, adv-*, set-bonus-*, form-basic-move, sm-mismatch-*, gear-*, armor-class-untrained, conditional-*-*, encumbrance) and drops any row with no modifier, description or duration.
13. Stun and facing penalties are applied inside `calculateCombatStats` and `calculateEncumbranceDetails`, not through the stunned effect's bag (empty on purpose); `defenseAdjustments` publishes stun+channel and the three availability gates.
14. `selectedParrySkill/selectedBlockSkill` and the active lightsaber Form's parry/dodge/block are applied by the UI layer (`uiStats` in use-character-form.ts), not by the engine; `parryOptions[].name` is a save key.
15. `rollAttributes(stats)` (`src/lib/roll-targets.ts`) is the only constructor of the branded RollAttributes bag; `bestSkillTarget(names, skills, attrs)` resolves Ch3's ladder including trained-level rollDeltas.
16. A droid's anatomy is derived from droidBuild (`droidAnatomy` + `reconcileDroidAnatomy`) and its SM from summed part heights (`deriveDroidSm`); stored hitLocations and sizeModifier are ignored for droids.

## rolls-hud

1. All target rolls are 3d6 resolved by `resolveRollOutcome(total, target, malfunctionThreshold)` (`src/lib/roll-outcome.ts`): 17/18 always fail, 18 always critical, 17 critical only at target ≤ 15, failure by 10+ is critical, 3–4 always critical success (5 at 15+, 6 at 16+), and a malfunction pre-empts a hit.
2. A malfunction range exists only when a weapon Malf threshold is passed (`malfunctionOrBase(durability, maxDurability)`: 17/16/15/14 by quarter of Durability remaining, Broken at 0); attribute, skill, power and defense rolls never malfunction. NOTE: for kit-built weapons `durability` is null (unmeasured) and the CARD's figure (`calculateBlasterStats(...).malfunction`, with the gas grade's modifier, min 4) is the one to use — see ARCHITECTURE §5.1.
3. `rollTargetNumber(label, target, modifier, rollType, pointsFormula, malfunctionThreshold, skillName, flawedItem)` returns {success, isMalfunction, isCriticalFailure, isCriticalSuccess, isAutomaticFailure, total, rolls, target, outcomeText, pointsText, numericEffect}; the card shows Skill / Target / Rolled [d,d,d] / Result lines, grenade scatter on failure, and a Ch10 ghost-glitch line on a natural 17/18 with a flawed item.
4. `rollDamage` parses formulas with `(\d*)d(\d+)?(?:[x*](\d+))?` per +/- part (default 1d6, type words ignored, armor divisors ignored) and clamps the total to a minimum of 1; volleys roll one 3d6 per shot and stop at the first malfunction.
5. RollButton is the universal trigger: total hit modifier = situational + skillBonus − skillPenalty + off-hand penalty (−4 attack / −1 parry-block when `dualWielding.penalized` and the Off-Hand toggle is on); a null target was coerced to 10 (Foundry refuses instead).
6. Targets are never hand-built: `rollAttributes(calculatedStats)` gives effective ST/DX/IQ/HT/Will/Per plus rollDeltas; `resolveSkillLevel(name, skills, attrs)` returns {level, source: trained|generalist|specialty|skill|attribute|none, from, penalty, attribute} for the Ch3 ladder.
7. Weapon attack targets come from `attackSkillFor(weapon, skills, attrs, hitBonus, skillBonuses)` → {target, skillTarget, hitBonus, type, requiredSpecialty} (`src/lib/weapon-attack-skill.ts`): lightsabers roll Lightsaber Combat (<classType>) with −1 for a sibling Class Type and DX−6 untrained, other weapons roll baseSkill with a DX−5 fallback; the Min-ST shortfall (`minStShortfallPenalty`, −1 per point short) is added at skill resolution so Parry moves with it; `attackHitBonus = modifiers.toHit + skillBonusFor(...).flat` — and `.target` ALREADY includes it (do not add it again).
8. Attacks bank hits: `pendingHits` (single/RoF/launcher), `lastVolley` (stinger darts), `firedRounds` (slugthrower rounds); the Damage button is enabled only while hits are banked and clears them; charges/rounds/darts/ordnance are deducted only for shots attempted before a jam; melee attacks stamp `lastAttackTurn = turnCounter` and set `isUnready` when `attackLeavesUnready` (Ch12 diamond rows below 1.5× Min ST), cleared only by the Ready button.
9. Stun (`stunType` Physical|Mental) hard-blocks every attack button, applies −4 to Dodge (inside dodgeBase) and to Parry/Block (defenseAdjustments); recovery is "roll HT or IQ, then dismiss the Stunned card"; the `stunRecovery` channel (+6 Combat Reflexes) is declared but never applied on the website (Foundry adds a recovery roll that applies it — a declared departure).
10. Dodge = floor(basicSpeed)+3 − encumbrance(0..4) − 4 if stunned + modifiers.dodge + active Form dodge (only while a saber is readied); Parry option = floor(level/2)+3 + narrowedParryBonus + stun + parry channel (Brawling and Unarmed (DX) carry a "−3 vs. armed" note); Block = same from Shield or Lightsaber Combat; the HUD rebuilds Parry/Block per chosen weapon adding finalParryMod, Form parry/block for sabers only, and the U/unready gates.
11. Facing is stored as two hexsides (facing, incomingBearing 0–5) plus threatEngaged, additionalBearings and facingChangeUsed; the arc is derived by `arcFrom` with Peripheral/360° vision shifts; Front allows all defenses, Side removes Block, Rear removes everything and counts as Flanked; facing gates defenses only.
12. Parry rolls increment `parriesThisTurn`, which drives a warn-only "Multiple parries" flag (−4 per successive parry) from `combatEconomyFlags` along with Vicious Cycle (EP below 1/3 halves ST), swing-EP below Min ST and Quick-Ready advisories; nothing in combat-economy.ts moves a number.
13. The turn sweep runs when turnCounter changes in either direction: facingChangeUsed → false, parriesThisTurn → 0, status effects with expiresAfterTurn < turn are removed with an "Effects Expired" toast; isUnready, lastAttackTurn, pendingHits and stunType are untouched.
14. Force power rolls use `forcePowerTarget(baseSkill)` and never spend FP; a separate Apply Costs deducts `calculateAdjustedFPCost(base, LS|DS|Grey, forceAlignment)` (Grey discount 0.5% × (25−|A|) only inside ±25, aligned powers ±0.5%/point beyond 25, round, min 1) and the catalog epCost.
15. Combat techniques roll either an unarmed best-of skill or a weapon bound to selectedWeaponId, with the row's skillBonus/skillPenalty/damageBonus and a separate Apply Costs; unarmed Punch and Kick share `unarmedStrikeTarget` (best of Brawling/Karate/Echani/Teräs Käsi, untrained DX−3) and damage from `unarmedDamage` (thrust + Karate +1/+2 per die only when striking with Karate, plus kickDamage).
16. Damage application is a separate manual step (Tactical Damage Processor, hit-location rows): DR minus typed DR, cut ×1.5, imp ×2, pi− ×0.5, pi+ ×1.5, pi++ ×2, head ×4 (droid ×2), vitals ×3 vs imp/pi, cold/stun/ion(organic) to EP, shock and sonic bypass DR; it writes HP/EP, degrades armour, stamps a Shock (−min(4,injury)) DX/IQ effect expiring next turn, cripples/severs locations and only PROMPTS the HT rolls.
17. Crew station actions come from `SHIP_STATION_ACTIONS` (six stations; Surgery/Diagnosis print no default) resolved by `bestSkillTarget`; ship weapon damage is `STARSHIP_WEAPONS_LIBRARY` damage + damageType; initiative is never rolled (Basic Speed with DX tie-break).
18. Roll history: `localStorage['shadowbase.roll-history']` {scope, rolls}, depth from `rollHistoryDepth` (10/25/50/100), gated by keepRollHistory; each entry stores title, plain-text description, resultText, timestamp.
19. Notifications: every toast becomes a NotificationRecord; the bell keeps notificationDepth (12/25/50) with at most depth−1 pins; pinned records are saved ON THE CHARACTER as `pinnedNotifications` [{id,title,description,variant,at}].
20.
